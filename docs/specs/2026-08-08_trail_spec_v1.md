# memex trail 명세 (v1)

2026-08-08 Fable 대화에서 합의. 배경: 검색은 매번 재계산하지만, 회상 세션이 "실제로 유용했던 문서"를 확인하는 검증은 이미 일어나고 있고 그 결과가 버려진다. trail 은 그 검증된 연결을 엣지로 저장해 재검색을 조회로 대체하는 층이다. canon 이 노드(사실)의 정제라면 trail 은 엣지(연결)의 정제 — 부시(1945) 원안의 trail.

## 0. 설계 원칙 (불변)

- **사서는 LLM 0개 유지.** 판단(어떤 문서가 유용했는가)은 회상 세션의 LLM+사용자가 이미 수행했다. 사서는 순수 집계만 한다.
- **세금 없는 자본화.** 영수증은 회상 대화의 부산물로 투함된다. 기록을 위한 별도 세션·별도 노동 없음.
- **온톨로지 금지.** relation 은 고정 3종에서 늘리지 않는다. 풍성한 스키마는 유지 못 해 썩는다. 길은 설계하는 게 아니라 밟혀서 난다.
- **state 는 재생성 가능해야 한다.** 집계 상태가 날아가도 processed/ 의 영수증 원본에서 완전 재구성된다 (reindex 와 같은 원리).
- 기존 우편함 원칙 승계: 인바운드 제로, 파일명 규칙 밖 무접촉, 16KB 상한, 오염은 격리.

## 1. Drive 구조 (추가분)

```
mailbox/
  trails/        # 영수증 투함함 (신규 폴더, folderId 생성 후 docs/mailbox.md 에 기록)
  processed/     # 처리 후 이동 (기존 폴더 공용, 보존·삭제 금지)
```

파일명 규칙: `t_{YYYYMMDDTHHMMSS}_{rand4}.json` — 규칙 밖 파일명은 무접촉 (기존 `q_*`/`c_*` 와 동일).

## 2. 영수증 프로토콜 (trails → 집계)

### 2-1. 영수증 스키마 (회상 세션 → 투함)

```json
{
  "type": "trail_receipt",
  "q": "원 질의 자연어",
  "used": ["대화파일명A.md", "대화파일명B.md"],
  "edges": [
    {"from": "대화파일명A.md", "to": "대화파일명B.md", "relation": "근거"}
  ],
  "note": "옵션 — 한 줄 맥락"
}
```

- `used` (필수, 1~10개): 검색 결과 중 **실제 대화에 쓰인** 문서만. 돌려받았지만 안 쓴 건 넣지 않는다.
- `edges` (옵션, 0~5개): 문서 사이 관계가 이번 대화에서 확인됐을 때만.
- `relation` 화이트리스트 **3종 고정**: `근거` (from 이 to 의 근거) · `후속` (to 가 from 의 후속) · `연관` (무방향, 기본값). 이외 값은 영수증 전체 거부.
- 노드 식별자는 **원본 파일명** — `promote_thread` 와 동일하게 **manifest 존재값만 유효** (경로 주입 차단). used/edges 안의 미존재 파일명이 하나라도 있으면 해당 항목만 드랍하고 사유를 로그에 남긴다 (영수증 전체 거부 아님 — 부분 수용).

### 2-2. 사서 처리 (mailboxd 확장)

기존 폴링 루프에 trails/ 추가. 흐름: 검증(16KB·스키마·파일명 규칙·relation 화이트리스트·manifest 대조) → 집계 state 갱신 → processed/ 이동. 오염은 기존 규칙 그대로: 깨진 JSON·스키마 위반 → 사유 로그 후 processed/ 격리, 파일명 위반 → 무접촉. **answer 는 쓰지 않는다** (영수증은 응답이 필요 없는 단방향 우편).

### 2-3. 집계 state

`~/memex/trail/trail_state.json` (상시 PC 로컬, Drive 백업 불필요 — processed/ 가 원본):

```json
{
  "as_of": "2026-08-08T12:00:00",
  "nodes": {
    "대화파일명A.md": {"count": 3, "last_used": "2026-08-08", "recent_queries": ["질의1", "질의2", "질의3"]}
  },
  "edges": {
    "대화파일명A.md|근거|대화파일명B.md": {"count": 2, "last_used": "2026-08-08"}
  }
}
```

- `연관` 은 무방향이므로 키 생성 시 파일명 정렬 후 결합 (A|연관|B == B|연관|A).
- `recent_queries` 는 최근 3개만 유지 (질의는 맥락이지 노드가 아니다).
- 재구성 커맨드: `rebuild_trail.py` — processed/ 의 `t_*.json` 전량 재집계. (명령 프로토콜 편입은 관망 — 우선 스크립트로.)

## 3. 회수 — 검색 응답에 병기 (P1)

search answer 의 각 hit 에 필드 추가 (스킬은 미지 필드 무시하므로 하위호환):

```json
"trail": {
  "uses": 3,
  "edges": [{"to": "대화파일명B.md", "relation": "근거", "count": 2}]
}
```

- `uses` = nodes count. **가치 점수 = 사용 횟수** — 별도 점수화 로직 만들지 않는다 (밟힌 횟수가 곧 길의 넓이).
- 순위 조작은 하지 않는다 (v1). trail 은 정보로 병기만 하고, 판단은 읽는 쪽 LLM 이 한다.

## 4. 스킬 개정 (memex-mailbox)

영수증 절 추가:

- **투함 시점**: 회상 결과를 실제로 대화에 사용한 뒤, 해당 작업 단위가 마무리될 때. 대화 종료를 기다리지 않는다 (종료 훅 없음 — 세션이 그냥 끊기면 유실이므로, 쓴 직후 투함이 원칙).
- **판단 기준**: "이 문서가 없었으면 이 답을 못 했다" 수준만 used 에 넣는다. 스쳐간 결과는 제외. edges 는 대화에서 관계가 명시적으로 확인된 경우만 — 추측으로 잇지 않는다.
- 투함 경로는 기존과 동일: 커넥터 우선, rclone 폴백.
- **P1 이후**: answer 의 trail 필드를 읽고 "이 문서는 과거 N회 사용, [B]의 근거" 를 회상 보고에 포함.

## 5. 단계

| 단계 | 내용 | 비고 |
|---|---|---|
| P0 | trails/ 폴더 생성 + 스킬 영수증 절 + 사서 수령·검증·집계 | 이것만으로 침전 시작 |
| P1 | search answer 에 trail 병기 + 스킬이 읽어서 보고 | state 가 어느 정도 쌓인 뒤 |
| P1.5 | 심도 축 — 영수증에 `depth` 실어 원문까지 읽은 회상을 구분 (§2-4) | P1 과 같이 |
| P2 | 1-hop 이웃 보너스 슬롯 — hit 의 엣지 상대를 검색 결과에 추가 (recent 트랙과 같은 별도 트랙, 정밀도 우선) | 관망 (진입 판단 = `trail_report.py`) |
| — | 하지 않는 것: relation 확장, 그래프DB 도입, 시각화, 순위 가중치, LLM 자동 엣지 생성, **심도 점수화(1~5)** | 밟히기 전에 길 넓히지 않기 |

**P2 진입 조건 (2026-08-13 실측으로 확정).** 그날 영수증 5통이 **전부 `used` 1개**였고 유기적 엣지는 0개였다 (엣지 1개는 P0 E2E 검증용 인공). 엣지는 한 회상에서 문서를 **둘 이상** 써야 나오므로, `used=1` 만 쌓이는 동안은 시간이 더 흘러도 엣지는 생기지 않는다 — 회상 질의가 "네이밍 뭐로 했지" 같은 **단일 사실 조회**면 문서 하나로 답이 끝나기 때문. 따라서 선행지표는 엣지 수가 아니라 **`used` 2개 이상인 영수증 건수**다. 이게 0에서 안 움직이면 P2 가 아니라 회상 사용 패턴(또는 스킬의 `used` 판단 기준)을 봐야 한다. 관측은 `scripts/trail_report.py` (state + processed/ 영수증 분석, 판정은 하지 않음 — 검증용/실회상 구분은 q·note 로 사람이).

## 2-4. 심도 축 (P1.5, 2026-08-13 사용자 요구)

trail 이 반영할 두 축: **빈도**(얼마나 자주 부르나 = `count`, P0 부터 됨)와 **심도**(얼마나 깊이 다뤘나). 심도는 **원문을 열었는가 하나만** 본다 — 스킬 절차 4단계(깊이 읽기)가 이미 카드/원문을 가르므로 그 사실을 관측만 하면 된다. 그 이상(대화를 얼마나 끌고 갔나 등)은 LLM 판단이라 노이즈가 많아 **넣지 않는다**. 점수화 금지는 canon 강도 규칙과 같은 선 — 자연 관측되는 이진 사실만 신뢰한다.

- 영수증 `used` 를 문자열 배열에서 `{"file": ..., "depth": "card"|"deep"}` 로 확장. **하위호환**: 문자열은 `card` 로 간주 (P0 영수증·구판 스킬 그대로 수용).
- `nodes[file]` 에 `deep_count` 추가 — depth=`deep` 회상만 +1. `count` 는 전체 회상(변경 없음).
- P1 병기에 두 축 노출: "N회 회상 중 M회 원문까지". 자주·깊이 판 문서가 자연히 굵어진다.
- `depth` 판정 주체는 회상 세션(스킬) — 원문 파일을 실제로 열었으면 `deep`, 카드 요약으로 끝냈으면 `card`.

## 6. 검증 시나리오

| # | 시나리오 | 기대 |
|---|---|---|
| 1 | 정상 영수증 투하 | trail_state 에 nodes/edges 반영, processed/ 이동 |
| 2 | 같은 edge 재투하 | count+1, last_used 갱신 |
| 3 | manifest 미존재 파일명 포함 | 해당 항목만 드랍 + 로그, 나머지 수용 |
| 4 | relation 화이트리스트 밖 (`유사`) | 영수증 거부, 사유 로그, processed/ 격리 |
| 5 | 깨진 JSON / 16KB 초과 / `t_*` 규칙 위반 | 기존 오염 규칙과 동일 (격리 / 무접촉) |
| 6 | state 삭제 후 rebuild_trail.py | processed/ 에서 완전 재구성, as_of 만 다름 |
| 7 | `연관` 양방향 투하 (A→B, B→A) | 동일 키로 합산 (count 2) |
