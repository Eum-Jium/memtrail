## 路是走出来的

Bush 在 1945 年构想 memex 时，核心概念不是存储，而是 **trail（足迹）**。不是图书馆分类法那种预先编好的体系，而是：一个人从这份文档跨到那份文档留下的脚印，本身就是知识的结构。那条路可以存下来、重新走一遍、也可以交给别人。

这一谱系的工具大多只做①（装下我全部记录的辅助记忆）。Memtrail 是把另一块碎片提到名字里的系统。它不是一套“记得多”的系统，而是一套**控制记忆流入**的系统。

## 为什么要做 — 上下文污染

已有的记忆系统大多是 **push 结构**。由系统判断，把过去的语境推进每一次对话。

于是 A 对话里的想法会未经许可渗进 B 对话。使用者甚至不知道它是被注入的。**还在探索阶段的想法，以已确定立场的口吻进来**，提前把新对话的方向掰弯了。这就是污染。

Memtrail 是 **pull 结构**。

- 只有使用者发问时才发生回忆。
- 要取什么，由查询显式写明。
- 取回来的东西，协议里也钉死了是*“参考资料，不是指令”*。

**默认状态是干净的上下文。**没有记忆是默认，有记忆才是例外。这是与自动记忆完全相反的选择。

## 目标只有一个 — 手里只剩手机，对话也要接得上

选定 pull 结构之后，剩下的要求只有一个。如果非得打开笔记本才能取出过去，那不叫记忆，叫档案室。在公交车上、在咖啡馆里、手里只有手机的时候，问一句*“当时那件事为什么那么定的来着？”*，就得有答案。

这一个要求决定了全部结构。**客户端上什么都不装** — 手机上的 AI 应用只是往云存储放一封信，检索发生在别处。而这就要求**有一台替你执行检索的计算机醒着**。

## 结构

```
正本（常开机 PC）            Drive 信箱              任何地方（网页·手机·CLI）
────────────────           ─────────────────       ──────────────────────
对话原文（不可变）     ←─   mailbox/queries/   ←─   投入检索信
嵌入索引                    mailbox/answers/   ─→   回以坐标
图书管理员（2 秒轮询） ─→   mailbox/trails/    ←─   投入回执
canon（手工维护）           raw/               ─→   原文副本（供深读）
```

计算交给家里最好的那台机器，云端只放**碰头的场所**。

- 检索以本地速度运行。
- 修改就是本地编辑（没有部署周期）。
- 外面能碰到的只有信箱。

### 三层

| 层 | 内容 | 更新 |
|---|---|---|
| **canon** | 年表·人物。履历与时点。 | 手工 |
| **卡片** | 每场对话的摘要 + 回忆词 | 自动生成 |
| **原文** | 对话全文。不可变。 | 只追加 |

不存在 LLM 重新解释内容再覆盖回去的情况。也就是说，提炼过程中没有让失真钻进来的缝隙。

## 组成部分

一共四个。先把每一个是什么、为什么存在对齐了再开始，会更快。

| 名称 | 实体 | 职责 | 需要常开吗 |
|---|---|---|---|
| **Memtrail 服务器** | 一台个人 PC | 保管索引 · 图书管理员守护进程 · 生成卡片 · 发布 | **常开（必需）** |
| **使用端设备** | 手机 · PC — 任何跑得动 AI 应用或网页的设备 | 提出回忆请求、接收回答 | 用时才开 |
| **被采集设备** | 产生代码会话的 PC | 采集本机对话并发往服务器 | 一天一次 |
| **Google Drive** | 一处云存储 | ① **信箱** ② **对话存储库** | 始终 |

**服务器和被采集设备可以是同一台机器。**如果写代码的那台 PC 能一直开着，那就是最简单的配置，届时下文“连接”一节的 tailnet 会整个消失。

### Memtrail 服务器 — 个人 PC

嵌入检索运行的地方。**手机上发问要有答案，这台机器就必须醒着，所以常开不是优化，而是前提。**信不会丢，但明天才到的回答不叫回忆。

不过它**既不是云服务器，也不是 VPS**。它干的活是嵌入检索，角落里一台低功耗迷你主机就够。嵌入、检索、排序全部在这台机器本地完成，既不用付费向量数据库，也不用外部检索 API。

这台机器上要登录着**订阅中的 AI CLI** — 只用来生成卡片（对话摘要），整个仓库用到 LLM 的地方仅此一处。**没有额外的 API Key，也没有按 token 计费。**

### 使用端设备 — 手机·PC 都行

**没有要安装的东西。**能在 Drive 写一个文件、读一个文件，就是全部。带连接器的 AI 应用直接就能用；没有的话，拿到 Drive API 授权也行。它不连接服务器，所以也不必加入 tailnet。

### 采集 — 两条路径各走各的

对话**留在哪里**不一样，采集的主体也随之分开。这是整个系统里最容易搞混的部分，所以用一张表钉在这里。

| 对话类型 | 记录所在 | 谁来采集 | 工具 |
|---|---|---|---|
| **网页·App 对话**（claude.ai） | 服务账号 | **服务器亲自来** | `collect_web_via_cdp.py`（需要已登录的浏览器配置文件）<br>或 `download_claude_conversations.js` → `unpack_claude_json.py` |
| **代码会话对话**（Claude Code） | **产生对话的那台设备的磁盘** | **该设备自己采集并 push 到服务器** | `unpack_claude_code_jsonl.py` → `collect_and_push.sh` |

左边绑在账号上，服务器可以独自取回；右边是本地文件，**服务器再怎么醒着也无从得知。**在笔记本上写了代码，就得由那台笔记本推进来。若只在服务器上写代码，这个区分随之消失，一个 `daily.sh` 收尾。

**推过去的不只是对话。**工作设备还会把它在本机冻存的**原件**（`archive/` — 会话 JSONL、收到的导出件）一并推过去。原件是重新导出 md 的唯一依据（→ [设计骨架 §1](#1-对话即正本)），而会话 JSONL 只在跑过那场会话的机器上生成、五周后消失 —— 留在那台机器上，就会随机器一起没了。只是它动辄数百 MB 起，所以不像对话那样整体推送，而是**只推上次成功 push 之后新冻存的部分**。

### Google Drive — 身兼两职

1. **信箱** — 使用端设备投入检索信、服务器投入回信的位置（`mailbox/`）。
   这是服务器不开任何端口也能与外界对话的唯一通道。
2. **对话存储库** — 原文副本（`raw/`）。图书管理员只返回坐标，使用端设备要翻到原文，副本就得放在这里。

正本永远在服务器本地，Drive 只是只读副本 — **不存在 Drive → 本地的自动路径。**

## 为什么没有把服务器开出去

**不是没试过，是试过了，所以才不开。**

我亲手做过一台回忆用的 MCP 服务器，放到云上跑。丢了三样东西。

- **慢。**嵌入检索吃算力和内存，而个人负担得起的价位段的 VM 撑不住它。
- **改起来费劲。**改一行代码都要走一遍部署周期。
- **门是开着的。**一个端口、一个认证漏洞被攻破，数年的对话就整块流出去。这不是一般数据，而是一个人全部的思考履历，损害的性质不一样。

信箱结构**把计算与接触点分开**，把这三样一并收回来。

> **MCP 不是被扔掉，而是被挪了位置。**去掉的是*亲手运营的那台回忆服务器*。客户端流程以[**技能**](skills/memex-mailbox/SKILL.md)实现，投递由早已装好的存储连接器完成。也就是从**“我自己拉服务器的 MCP”变成“用现成 MCP 的技能”**。要点是：要维护的服务器少了一台。

### 安全

图书管理员守护进程**只做出站轮询**。

- 开放端口 0 个。不做服务器托管。不做隧道。没有暴露的 API 端点。
- 从网络上压根没有可以走进来的门。
- 攻击面是 Google 账号，而那由 Google 的 2FA 与异常登录检测把守 — 比个人自建的服务器认证更结实。
- 就算被攻破，Drive 上的也只是副本。反过来，正本机器死了，也能从 Drive 重建（→ [重新架起来](#7-重新架起来--机器没了的时候)）。

诚实的一句：**正本机器本身被拿下，就是真的完了。**那是设备卫生的份内事。

默认开着的东西，以及**不做的事**：[`docs/security.md`](docs/security.md)

### 隐私 — 先把威胁模型说清楚

**Memtrail 不往信任清单里添加新的服务器，也不添加新的公司。**

云端记忆服务归根结底是在说*“请再信任这家公司”*。Memtrail 的数据不会离开你本来就在用的 Google 账号。认证、加密、2FA 由 Google 扛。**新增的信任对象是 0。**

不夸大。准确的说法是*“不添加第三方”*，而不是*“Google 也看不到”*。静态加密的密钥握在 Google 手里。收到搜查令可以交出去，账号被停用则访问被切断。**“不看”和“看不到”是两个层面。**

你的记忆放在你本来就在用的存储里。要多信任那个存储是你的选择，而这个选择通过**更换 rclone 后端**来执行。

### 连接 — Tailscale 为什么掺进来

只看回忆路径，服务器**一个端口都不需要开**。它只是向外轮询 Drive，手机也只碰 Drive。到这里为止，压根不存在直接互连的区段。

问题出在**采集**。代码会话对话只在工作设备的磁盘上，必须由那台设备向服务器**推送**，而那是真正的机器对机器连接。在这里套用常见解法，前面守住的一切会一次崩塌 — 端口转发和 DDNS 会把装着毕生对话原文、24 小时开机的机器送进互联网扫描器的射程；中转 VPS 则把别人的基础设施放进了信任路径。

**[Tailscale](https://tailscale.com) 让这条连接不需要端口。**它是基于 WireGuard 的私有网络，两台设备**各自向外走、在外面碰头** — 对服务器而言依旧只有出站连接，开放端口保持 0 个。新设备在你本人批准之前，进不了 tailnet。

用到 tailnet 的位置**只有两处**：① 工作设备 → 服务器 push；② 家外 → 服务器管理（看日志、重启守护进程、重建索引）。**使用端设备（手机等）不需要加入 tailnet** — 因为它只用 Drive。为了回忆去接触服务器这种事，设计上就不存在。

> **也有完全用不到 Tailscale 的配置。**如果写代码的那台 PC 能一直开着，**让它当服务器就行**。对话本来就在那块磁盘上，要 push 的东西、机器对机器的连接、tailnet，全都消失 — 一个 `daily.sh` 收尾。
>
> **而且这种配置在安全上也更好。**两种配置的开放端口都是 0 个，但单机配置在此之上又薄了一层 — 没有理由跑一个接收用的 SSH，不用往 tailnet 里加设备，也不用在设备之间存放和管理密钥。**连接本身不存在，就不可能经由这条连接被攻破。**
>
> 分界线不是“常开”的意愿，而是**那台机器守不守得住位置**。台式机成立。笔记本被拎出门或合上盖的瞬间，回忆就断了，这时才需要单独安置一台“守在原地的机器”，再用 tailnet 连起来。

### 这不是巧合

无服务器（安全）与防污染（思想），是**从同一个设计决定里一起掉下来的结果**。

正因为回忆是显式请求，它才被实现为轮询 + 等回信这样的消息传递。若是自动注入结构，就需要常连接，根本做不成信箱。

**顺带得到的是可移植性。**信箱客户端的要求只有*“能写一个文件、读一个文件”*，接入路径因此有了双保险 — 存储连接器在多数 AI 产品上本来就带，集成工作量为 0；没有的环境，拿到存储 API 授权即可。协议标准就算十年换一茬，**“写文件”这个契约不会变。**

## 设计骨架

### 1. 对话即正本

积累的不是摘要，是**原文**。卡片（摘要）只是为加速检索叠上去的一层，任何时候都能沿原文坐标（文件 + 轮次编号）下潜。一旦整理成笔记，“为什么得出那个结论”就没了 — 这个结构堵住的正是这个问题。

**而且，连 md 也已经是派生物。**转换器丢掉了什么，总是事后才知道 — 曾经一天之内暴露过四次（画布正文、712 个工具调用块、附件文件名、发言时刻）。原始 JSON/JSONL 还在，就能修好转换器重新导一遍；不在，就到此为止。所以收到的原件不删，冻存进 `archive/sources/`。

### 2. 回忆走信箱（唯一的接口）

检索不是服务，是**异步邮件**。任何客户端往 `mailbox/queries/` 投入一封检索信（JSON），图书管理员守护进程读到后，在 `mailbox/answers/` 以**坐标**作答。

这套系统五条设计原则里的三条都出自这里 — 零入站 · 正本单向（没有 Drive→本地的自动路径） · 白名单执行（不把自由文本解释成命令）。

图书管理员**不使用 LLM** — 只有 E5 嵌入 + Chroma + BM25，廉价而确定。
设计依据：[ARCHITECTURE.md §0](ARCHITECTURE.md#0-왜-우편함인가)

### 3. 检索不是去读，而是查预先建好的索引

不会每来一个问题就去读对话。**采集阶段已经把全部对话切块、嵌入、放进了向量数据库（Chroma）**，图书管理员只是查询那份索引。所以不用 LLM，几万块的规模也在秒级完成。服务器可以只是一台低功耗迷你主机，原因就在这里。

相关度**分四路打分再混合**。

| 轨道 | 度量什么 | 分数 |
|---|---|---|
| **dense** | 语义相似度 — E5 嵌入余弦距离 | `1/(1+距离)` → 0~1 |
| **BM25** | 词面是否真实重叠 | 按与榜首之比截断，分数为 `null` |
| **最近** | 最近 90 天 ∩ dense 前列 ∩ BM25 下限 | `null` |
| **最新** | 命中集合里**最晚的那次提及**（不是绝对窗口） | `null` |

各条轨道轮流各取一条（交错），**同一场对话只进一次** — 去重必须按对话而不是按块，否则前 5 名会被同一场对话的碎片占满。

为什么不能只靠一条？因为“只靠一条不行”是实测教出来的。

- **只有 dense** — E5 的相似度带窄在 0.72~0.83，无关对话会被捎上来。
- **只有 BM25** — 常见词重叠的离谱对话会浮上来（实测：查询*“AI 模型比较”*，返回主题毫不相干的对话）。
- **最近轨道** — 只用全局排名，同一话题聊得久了，旧对话会垄断前列。所以只给最近 90 天内语义、词面**两头都满足**的块留一个席位。
- **最新轨道** — 最近轨道是绝对的 90 天窗口，抓不到*比这更早之前就变过的当前值*。见下文「把审议读成了确定」。

带日期、来源条件时，先在索引层过滤，再打分。

回答里连同分数一起，标明**从哪条轨道命中**（`match`）。BM25、最近、最新命中的分数是 `null` — 它们不是因为相似，而是因为**那个说法真实存在**才被抓到，所以用专有名词或精确表述发问时，反而常常是这一路才对。

### 4. 被踩过的路会变粗（trail）

见下文[单独一节](#trail--验证过的使用而非访问频度)。上面的分数是*“此刻算出的相似度”*，trail 则是*“过去真实有用过的履历”*，性质不同。两者一并随答案送出。

### 5. 正本层（canon）

履历、决定、人物、年表这类**不容出错的事实**，不靠检索重新挖掘。先读手工维护的一页 `canon.md`。每个条目都挂着证据等级，已确认的事实与未确认的推测不相混。

没有这一层的时候，复原一段很久以前的履历花了 3 次检索 + 2 次原文直读，事实还是错了。**承认检索有干不了的事，才建了这一层。**

## trail — 验证过的使用而非访问频度

自动记忆的注入是**没有验证的重复**。存进去的东西，对也好错也好都会一直涌进来，注入得越多就越固化。

trail 反过来。**只有回忆结果真被用进了回答**，而且是被回执明确确认过的，才计入。

```json
{"type":"trail_receipt","q":"原始查询",
 "used":[{"file":"对话A.md","depth":"deep"}],
 "edges":[{"from":"对话A.md","to":"对话B.md","relation":"근거"}]}
```

- `uses` — 被翻出来看过几次（**频度**）
- `deep_uses` — 其中没停在卡片摘要、一直翻到原文的有几次（**深度**）
- `edges` — 只记录在对话里**被明确确认过**的关系（`근거`（根据）·`후속`（后续）·`연관`（关联））。不靠推测连线。

检索结果会把这份粗细一并标出。它是把**验证过一次的连接变成查询**的装置，用来替代每次重算相似度。Bush 说的 trail，正是这个。

强化一类的实现大多**只要被检索命中，计数就往上走 — 那是访问频度**。Memtrail 过滤的是“有没有真的被用进回答”。这个区分就是这套系统的中心。（它的结构与生物记忆的再巩固相似 — 每用一次路径就被强化，不用的连接自然变弱，深加工过的记忆更牢固。不过这是比喻，不是建模。）

一条原则：**路没被踩过，就不拓宽。**不自动生成边（LLM 推理），也不引入图数据库。只有真实发生过“一次回忆同时用到两份文档”，边才会出现。
设计依据：[`docs/specs/2026-08-08_trail_spec_v1.md`](docs/specs/2026-08-08_trail_spec_v1.md)

## 记忆知道什么、不知道什么

回忆要诚实，就得**能把不知道说成不知道**。为此专门配了几个装置。

- **证据等级** — canon 的条目分为 `[本人注明日期]` 与 `[未确认]`。不靠推测去填。
- **coverage** — 每封回信都带上各来源的最新索引日期。*“还没建索引”*与*“那天没有记录”*是两回事，不含混带过。
- **谱系模式** — *“这句话最早是什么时候说的”*，按分数排的检索抓不到，因为聊得最透的那场会占住前列。为此需要一个单独的模式：只收集词面确认过的对话，按日期升序返回。
- **`summary_kind`** — 区分收到的是 LLM 摘要还是原文片段。拿原文片段去推断一场对话的结论，会推错。

## 实测失败记录

这也许是本仓库里最有用的部分。**设计全部出自事故。**

**回忆词选错（2026-08-15）** — 问一件事时用了**词典上那种正式说法**，全部空转。原文里写的是当时亲历时实际在用的**口语和缩写**。指的是同一件事，字面却一个都不重合。不是采集有洞，而是词汇选择失败。→ 卡片因此有了**回忆词字段** — 通读整场对话，再把“日后要找它时可能会用的说法”单独记在卡片一侧。

**抓不到最早提及（2026-08-20）** — 一个概念的起点答成 6/27，实际是 5/22。dense 前 400 条的分数跨度只有 0.07，分不出相关与无关。这类噪声在普通检索里被埋着，一按日期排序就冒到最前面。→ **谱系模式要求词面确认的原因。**

**把审议读成了确定（2026-08-25）** — 问*“我现在的<当前值>是什么来着”*，把分数最高的那场几年前的**审议**对话原样搬了出来。实物并非如此。**审议长而确定短** — 挑了二十轮的候选，在分数上赢过了定下来之后只被顺口提过一句的实物。→ 回信因此加上了**按日期升序的时间线视图**和**最新轨道**。

**信了标题，把命中丢掉（2026-08-25）** — 只看第一个问题就自动生成的标题底下，是一场 222 轮的对话。检索取回的是对的，**是读的这一侧把它扔了。**→ 卡片因此要**通读全场再重新拟标题**。

**误判了原件消失的原因（2026-08-26）** — 代码会话的原始 JSONL 只在某个日期之前缺失，于是写成了*“过 5 周就过期”*。错了。换工作设备时，旧机器被格式化了。含义恰好相反 — 若是过期，5 周内收好即可；而**换机器一定还会再发生、损失是 100%、且毫无预告**。250 场对话之所以活了下来，是因为每天转成 md 推了进来；丢掉的是只存在于原件里的发言时刻和工具调用细节 — **对那 250 场，转换器的改进永远无法追溯适用。**→ 原件因此被冻存进 `archive/sources/`。

**用属性词去问一个人（2026-08-27）** — 问*“我的<人物属性>是什么”*，用那个属性词和它的近义词去问，连错三次。真正在做那件事的人不会用那个属性词，他就只是去做。真正的答案和猜测完全不同，而语料里那件事的记录已经堆了好几个月。**一个人的属性，不在出现那个词的对话里。**→ 客户端流程因此改成用**动作词**而不是属性名去问。

这些是样本数为 1 的发现。等别人也开始跑起来，失败案例会多出十倍，而那正是改进设计的原料。

## 快速开始

### 1. 克隆 + 环境

```bash
git clone https://github.com/Eum-Jium/memtrail.git
cd memtrail

python -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate

pip install -r requirements.txt
```

### 2. 指定数据位置

代码与数据是分离的。数据放在**仓库之外**。

```bash
cp .env.example .env
# 把 .env 的 MEMEX_DATA_DIR 指向你自己的数据位置
```

```
$MEMEX_DATA_DIR/
├── conversations/   # 对话原文（正本）
├── cards/           # 每场对话的卡片
├── memory_db/       # ChromaDB
├── canon/           # 手工书写的正本层
├── archive/         # 原件（导出 zip · 会话 JSONL · 附件）
└── trail/           # 回执沉淀物
```

### 3. 首次摄取

```bash
# claude.ai — 在已登录的浏览器 F12 控制台粘贴 download_claude_conversations.js
# 再解包拿到的 json
python unpack_claude_json.py ~/Downloads/claude_conversations_<日期>.json

# Claude Code 会话（JSONL → md）
python unpack_claude_code_jsonl.py --out $MEMEX_DATA_DIR/conversations

# 建索引
python memory_pipeline.py $MEMEX_DATA_DIR/conversations $MEMEX_DATA_DIR/memory_db
```

### 4. 生成卡片（可选）

```bash
python scripts/build_memory_cards.py
```

**用的就是你已经在订阅的 AI。**方式是以 `-p` 调用已登录的 `claude` CLI，所以既没有单独的 API Key，也没有 token 计费。整个仓库用 LLM 的地方只有这一处。

没有就静默向下降级：CLI 未登录则用 `ANTHROPIC_API_KEY`（这条路要计费），再没有就用**摘录桩** — 只是卡片没那么好看，流水线不会停。模型默认值是 haiku（以 98 张追溯生成验证过质量）。

话题标签不是自由生成，而是从 [`config/topic_vocab.md`](config/topic_vocab.md) 的受控词表里挑。因为放开自由生成的结果是：344 个唯一标签里 81% 只出现过一次，频度统计本身无从谈起。

仓库里那份列表是示例。**自己的话题放进 `$MEMEX_DATA_DIR/config/topic_vocab.md`，以那边为准** — 个人关注清单不必提交进仓库。

### 5. 架设信箱

**要真正用上回忆，必须走到这一步。**前面各步是在积累数据，信箱是把它取出来用的唯一窗口。

服务器端的信箱往返全部经由 [rclone](https://rclone.org) — **用 rclone 远程路径寻址，
而不是文件夹 ID。**① 安装 rclone → ② 用 `rclone config` 创建 Drive 远程（如 `gdrive:`）→
③ 在 Drive 的 `ClaudeMemory/mailbox/` 下建好
`queries/ answers/ commands/ trails/ receipts/ processed/` 文件夹；远程名不同时在
`.env` 里设置 `MEMEX_DRIVE_REMOTE`。然后：

```bash
python scripts/mailbox_daemon.py
```

（写进客户端技能（SKILL.md）的文件夹 ID 是**客户端**的地址 — 连接器 `create_file`
所用的 parentId。服务器不使用 ID。）

**这台就是常开机的 PC。**手机上发问要有答案，这个进程就得醒着。（它关着，信也不会丢 — 信件留在文件夹里，开机后从积压的开始处理。但*明天才到的回答不叫回忆。*对话当中用不上，就等于没有这个功能。）

开机自启：macOS 用 `scripts/com.memex.mailboxd.plist`（launchd），Linux 用 systemd unit，Windows 用任务计划程序 — 挂上同一条命令即可。

客户端这边没有要安装的东西。能访问那个存储 — 走连接器也好、走 API 也好 — 就到此为止了。

协议详情：[`docs/mailbox.md`](docs/mailbox.md) ·
客户端流程：[`skills/memex-mailbox/SKILL.md`](skills/memex-mailbox/SKILL.md)

### 6. 挂上每天要跑的任务

**在常开机的 PC 上** — 采集 → 增量索引 →（月初画像）→ 重新生成卡片 → 密钥扫描 → 上传 → manifest：

```bash
bash scripts/daily.sh
```

**若另有工作设备（笔记本等）** — 在那台设备上进行的 CLI 对话只在它的磁盘上，所以要采集后推送到常开机的 PC：

```bash
bash scripts/collect_and_push.sh
```

在 `.env` 写上常开机 PC 的 ssh 别名（`MEMTRAIL_SERVER`）即可。传输只发生在 tailnet 内。没有变更时，两边都会整体跳过。

两边都挂到操作系统的调度器上 — **错过补跑的选项务必打开**（如任务计划程序的 `StartWhenAvailable`）。尤其别把笔记本的任务排在凌晨 — 整夜关机，每次都错过。

Windows 工作设备把 [`scripts/run_collect_and_push_hidden.vbs`](scripts/run_collect_and_push_hidden.vbs) 注册进任务计划程序即可 — 直接挂 bash，每次都会闪出控制台窗口；这个包装器以隐藏窗口运行，并把退出码原样传回调度器。注册命令在文件头部注释里。

图书管理员守护进程（第 5 步）独立于这些任务常驻。这边负责积累，那边负责取用。
流水线详情：[`docs/drive_sync.md`](docs/drive_sync.md)

### 7. 重新架起来 — 机器没了的时候

**这份文档对不对，只看文档重建一次就知道。**实际删掉文件夹、只照着这一节重建并验证过三次。**卡住了，那就是文档的 bug — 改好并提交。**

流程与快速开始相同，**只有一步不一样** — 把③首次摄取换成恢复：

```bash
# ①② 克隆 + 环境 + .env 与上文相同。先连好 rclone 远程（见⑤），然后：
python scripts/restore_from_drive.py                 # Drive → 本地（目标文件夹必须为空）
python scripts/dedupe_sessions.py --apply --cards    # Drive 上还留着被删的重复会话，会复活
python scripts/rebuild_memory_db.py --md $MEMEX_DATA_DIR/conversations --out $MEMEX_DATA_DIR/memory_db
                                                     # 索引是派生物，重建即可（实测约 16 分钟）
```

连仓库都没有的情况下 — 只把 [`docs/drive_sync.md` 里的 rclone 七行](docs/drive_sync.md)粘过去，数据也能回来（不需要 Python）。

无法自动化的，只有**人手里的三把钥匙**：Google 账号（rclone 重新认证）、claude CLI 登录、`.env` 那几行。保险柜的钥匙放不进保险柜里 — 只要这三样不丢，其余全部靠上面四行重建（2026-08-15 实测：服务器数据整体删除 → 33 分钟归位；工作设备文件夹整体删除 → 恢复后对话集合完全一致）。

## 信箱协议

```
客户端                               图书管理员守护进程
─────────────                        ─────────────────
q_{id}.json ─→ queries/  ─────────→  2 秒轮询 → 验证（16KB·schema·文件名）
                                     → E5 嵌入 + Chroma + BM25 交错
                                     → 附注 trail 粗细
a_{id}.json ←─ answers/  ←─────────  返回坐标（卡片摘要·文件 ID·锚点）
                                     → 处理过的信件保存于 processed/

t_{id}.json ─→ trails/   ─────────→  汇总回执（不回信）
c_{id}.json ─→ commands/ ─────────→  管理命令（白名单 4 种）
```

管理命令只有 `promote_thread`·`quarantine_list`·`quarantine_adopt`·`reindex` 四种，除此之外一律以 rejected 回执驳回。**信箱是一道信任边界。**

## 技术栈

- **语言** — Python 3.10+
- **向量数据库** — [ChromaDB](https://www.trychroma.com/)（长期考察 `sqlite-vec`）
- **嵌入** — `intfloat/multilingual-e5-base`（韩语表现优秀，768 维）
- **词面检索** — BM25（与 dense 交错）
- **卡片生成** — 订阅中的 `claude` CLI（`-p`）。只有这一层用 LLM，没有则回退到桩
- **图书管理员守护进程** — 一个 Python 进程。跑在常开机的个人 PC 上
- **存储格式** — 只有 Markdown · SQLite · JSON。因为 30 年后也必须读得出来

## 设计原则

1. **毕生资产** — 以运行 30 年以上为前提。格式的长寿优先于性能。
2. **数据隔离** — 代码与数据分离。数据位置由环境变量指定。
3. **本地优先** — 嵌入、检索全部本地计算。外部 LLM 只用于生成卡片，而且是可选的。
4. **路没被踩过就不拓宽** — 不为未被观测到的需要预建结构。
5. **失败要留日志** — 不留就会误诊病因。
   （以为是超时的 71 件，全是提示词的问题。）

## 它不是什么

- **不是万能记忆。**它以运维纪律为前提。正本机器要一直开着，canon 要手工维护。
- **读取不是免费的。**提炼过的 wiki 式文档，一次性载入上下文就完事；Memtrail 有检索往返，还有回忆词选错的风险。**这是选了忠实度、拿读取速度去付账的设计。**canon 就是减少这笔付账的装置。
- **不擅长综合类提问。***“我在这个话题上的立场整体是怎么梳理的”* — 这种问题，提炼过的文档比命中列表更合适。如果这一点开始经常疼，那就按话题多加几层像 canon 那样的提炼层 — 扩展路径本来就在里面。
- **不是通用库。**它是一个人的实际在用系统的公开版。`config/topic_vocab.md`、信箱地址之类的东西，得换成你自己的。这不是限制，而是**邀请你 fork 过去随便拆改** — 它是 Apache 2.0。

## 关于名字

这个项目长期以 `memex` 之名生长。名字取自 Bush 在 1945 年勾画的 *memory extender*，代码里的标识符（`MEMEX_DATA_DIR`、`skills/memex-mailbox` 等）至今仍留着它。

对外改名 **Memtrail**，理由有二。

1. `MEMEX` 在韩国已被人以软件类别（第 9 类）在先注册为商标。顶着这个名字发布，风险太大。
2. 更重要的理由 — **trail（足迹）才是这套系统真正的差异点**。Bush 构想的两根柱子，①是装下我全部记录的辅助记忆，②是 *associative trail*，而这一谱系的工具大多只做①。Memtrail 把②[真正实现了](#trail--验证过的使用而非访问频度)。

`mem` 留下，`trail` 接上。就名字的含义而言，改名反而更贴近原典。

新名字也查过了。`jrfonseca/memtrail` 是一个基于 LD_PRELOAD 的 Linux 内存分析器，比这个项目更早 — 但领域完全不同（系统编程 vs AI 智能体记忆），真实用户不会搞混。没有以同名注册的商标。
